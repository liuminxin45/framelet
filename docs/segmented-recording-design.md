# 最长单段 300 秒的可靠轮转录制

状态：原始设计记录，第一阶段已实施。日期：2026-11-02。以本方案的 300 秒单段上限替代总体演进方案中建议的 60 秒常规分段；本阶段聚焦可靠保存，不增加高帧率、视频编码或自动合并能力。

实施进度：本轮已实现第一阶段，实际入口、产物与边界以 [long-recording.md](long-recording.md) 为准。CLI 采用独立 record-series、MCP 采用 framelet_start_series；新增 segment.json 段凭据，检查点采用有界完整快照。本文其余内容保留为原设计记录，不作为当前命令参考。

## 1. 行为与范围

- 新增显式“分段录制”模式，每个 GIF 播放时长不超过 300 秒，到点自动保存并继续下一段。该 300 秒是轮转阈值，不是任务结束、错误或 MCP 调用超时。
- 同次录制可以持续 600 秒、650 秒或更久，直到用户停止、总时长或资源预算到达。例：650 秒正常录制产生 300 + 300 + 50 秒三个 GIF；恰好 600 秒产生两段，不额外创建空第三段。
- 普通单 GIF 模式、原有命令默认行为和文件名保持兼容；分段模式从第一段就采用专属目录和 part 编号，即使实际只录制了 20 秒也不退回普通单文件命名。
- 继续默认记录键盘、鼠标和帧的唯一标识、原始 UTC 与单调时间。轮转不重启键鼠 hook，也不重置整次录制的观察序号。
- 一段可能因容量、事件数或元数据预算提前结束，因此保证“最长 300 秒”，不承诺每段一定是 300 秒。
- 本阶段保留现有 1–50 FPS 和像素预算；不同时扩大性能边界。现有 GUI 暂不暴露新模式，CLI 和 MCP 使用同一个任务内核；GUI 后续接入时复用该实现。

## 2. 文件命名：一看就知道是同一组

默认目录和文件如下。用户指定友好名称 bilibili，软件加本地开始时间和随机短标识生成组名：

```text
D:\Captures\
  bilibili.gif                                      普通单 GIF 模式
  bilibili__20261102-153000__7c91a2bf.framelet\       一次分段录制
    recording.json                                 录制索引与汇总
    bilibili__20261102-153000__7c91a2bf.part-000001.gif
    bilibili__20261102-153000__7c91a2bf.part-000001.timeline.json
    bilibili__20261102-153000__7c91a2bf.part-000001.capture.json
    bilibili__20261102-153000__7c91a2bf.part-000002.gif
    bilibili__20261102-153000__7c91a2bf.part-000002.timeline.json
    bilibili__20261102-153000__7c91a2bf.part-000002.capture.json
    bilibili__20261102-153000__7c91a2bf.part-000003.gif
    bilibili__20261102-153000__7c91a2bf.part-000003.timeline.json
    bilibili__20261102-153000__7c91a2bf.part-000003.capture.json
    .work\                                         未提交段与恢复信息
```

命名规则：

1. 同组所有媒体保留相同名称、开始时间和短标识前缀；单独复制一个 GIF 也能看出组别和顺序。前缀不能仅有日期或文件名。
2. 段号从 000001 开始递增，不在中途写入未知的总段数，也不在结束时批量重命名。段号允许大于六位，不截断、不复用；失败段保留状态，不能把编号悄悄交给另一个内容。
3. 本地时间用于阅读；清单另存原始 UTC、时区和完整随机 session ID。短标识不是身份或鉴权依据，目录以 create-new 方式创建，碰撞则重新生成。
4. 每段还有独立 segment ID 和 asset ID；文件名只是展示，不作为键鼠帧关联主键。改名、复制后的关联以清单/时间线标识和内容哈希为准。
5. 名称限制长度并拒绝路径分隔符、Windows 保留名和非法字符；路径全长在开始前校验。不能为了“容错”把越界路径改写后继续保存到意外位置。
6. 已提交 GIF 可直接用普通查看器打开，时间线和校验文件与它一同复制才能保留完整追踪能力。

## 3. 时间语义

| 时间 | 定义 | 用途 |
| --- | --- | --- |
| 单段媒体时间 | 当前段实际保留的 GIF 时间，暂停不计入 | 到 300 秒轮转 |
| 全局媒体时间 | 各段连续的录制播放时间，暂停不计入 | 定位某次操作属于哪一段 |
| 墙钟时间 | 从正式任务开始经过的真实时间，含暂停和故障间隙 | 防止无界任务、诊断 |
| 原始输入/采样时间 | UTC 加单调观测时间与采集区间 | 真实键鼠帧关联 |

倒计时不计入媒体时间。暂停保持当前段，不为了时间流逝创建空段，但墙钟保险上限继续计时。停机、睡眠或来源失效的缺口不伪装成正常录制；默认保存并结束，原因写入索引。

任务总录制时长与单段长度是不同配置：`duration:600` 表示整次录制目标 600 秒，`segment_seconds:300` 表示单段最多 300 秒。分段模式不继承普通模式的 5 秒默认值，必须提供 duration 或 until_stop，二者互斥。duration 是目标媒体时长；长时间暂停仍可能先到墙钟上限。

GIF 使用厘秒时间轴：每段最大 30,000 个厘秒。跨边界的停留区间拆开分配，不把一帧完整时长推入上一段导致超过 300 秒。调度/编码耗时不能通过延长 GIF 或假造采样来掩盖。

## 4. 轮转流程与连续性

```text
创建录制组、启动键鼠观察与连续采集
    ↓
写入 part-000001
    ↓ 到 300 秒 / 提前触发容量或元数据轮转
冻结第一段的媒体边界，路由后续数据至下一段
    ├─ 第一段收尾 → 校验 → 提交 → 更新 recording.json
    └─ 第二段准备完整首帧 → 继续写入
    ↓
重复，直到用户停止或总预算到达
    ↓
保存最后一段 → 提交索引与最终状态
```

- 采集服务和键鼠观察连续运行，不通过“停止整个录制进程再启动一次”实现轮转。编码端切换 GIF writer。
- 下一段第一帧必须是可独立解码的完整画面，不能只存依赖上一段的差分矩形。
- 使用有界流水线，最多一段正在写、另一段正在收尾；加上少量有明确字节预算的边界缓冲。不允许因连续轮转积累任意多个收尾任务。
- 常规轮转不等待全部校验完成后才恢复采集。若收尾/写盘持续堵塞，记录丢帧或间隙，并停止为 partial；不能无界堆积内存，也不能无提示丢帧。
- 目标是正常负载下边界不出现额外丢帧；这是需要实测的验收项，不能预先承诺硬实时无缝。为新段补齐完整首画面时若复用已有采样，必须保留该采样原始时间与来源标识，不生成假采样。
- 用户停止与轮转同时到达时，停止优先：保存已有内容，检查是否还有有效数据再创建下一段。恰到总时长边界不产生空 GIF。
- 单段采样/事件数组落盘后释放，任务层仅保留有界摘要及索引，内存不随总录制时长线性增长。

## 5. 可靠保存：已提交段与当前段分别保护

### 5.1 每段提交

写入 .work 下独占创建的临时文件 → 结束 GIF、刷新文件 → 完成时间线 → 写入哈希校验清单 → 发布该段文件 → 原子替换录制索引中的已提交列表。

索引使用同目录临时文件、刷新、受控替换和代次号，保留上一份有效索引以便恢复。段文件使用不可覆盖发布；可更新的录制索引需要单独实现安全替换，不能直接复用“目标不得存在”的发布接口。

多文件本身不是原子事务。分段完整性由校验清单和最后提交的索引决定；若 GIF 已发布而索引未更新，下次恢复发现并验证这个孤立段，幂等补全索引，不重复录制。若仅媒体有效、元数据失败，明确返回 media_saved / metadata_failed，不谎称全部失败或全部成功。

### 5.2 段内恢复检查点

仅每 300 秒收尾仍会使异常时损失接近 5 分钟，因此当前段建议约每 5 秒建立一次检查点：

- 将已完成的 GIF 图像块、事件日志和映射日志刷新到磁盘；检查点记录安全字节边界、日志偏移、帧数、有效媒体终点与序号。
- 对静止画面也定期结束可提交的停留区间，不能因编码器一直合并静态帧而 300 秒不实际提交任何新数据。该策略会增加少量重复帧，属于可靠性成本。
- GIF、事件/映射日志先刷新，最后更新检查点。只有具有完整帧映射的数据前缀才可声明为可恢复，后到的输入事件保留为未映射或尾部日志。
- 正常停止先完成最后一个有效区间，不受 5 秒粒度限制；检查点是异常恢复机制，不是固定截掉尾部。
- 异常恢复从原文件复制出安全前缀，在确认完整 GIF 块边界后补合法结束标记，独立解码、验证并生成恢复段；不能仅追加结束字节就宣布文件正确。原始残片保留作证据。
- 正常磁盘条件下以约 5 秒恢复窗口为目标，报告最后成功检查点时间；不承诺断电、坏盘或同步调用卡死时绝对最多丢失 5 秒。检查点持续落后会触发故障处理，不能保持“健康录制”假象。

### 5.3 异常处置

| 情况 | 处理 |
| --- | --- |
| 用户 stop / Ctrl+C | 请求保存并结束，返回保存结果或 finalizing；可继续查询 |
| 正常 MCP EOF / 断连 | 请求停止并保存，不再按 cancel 丢弃当前段；若父进程被直接终止则走恢复 |
| 用户 cancel | 取消未提交尾部；已提交段保留，结果标明取消范围；整组删除另行显式操作 |
| 进程崩溃 / 被杀 | 已提交段保留；下次发现检查点并恢复当前段，不自动继续采集 |
| 磁盘接近预算 | 提前收尾并停止，返回 disk_budget；不自动删除旧段 |
| 磁盘满 / 权限失效 | 尝试保存可写的有效内容；保留残片，报告准确失败阶段和路径；不循环重试 |
| 屏幕来源失效 / 睡眠 / 锁屏 | 尽力收尾，保留已提交段；记录来源失效/观测缺口，不自动迁移至其他屏幕 |
| 编码或 worker 超时 | 监督进程结束失效 worker，保留可恢复数据；不反复重演用户操作 |
| 校验/索引发布失败 | 录制结束为 partial，列出可查看媒体、元数据问题及恢复建议 |

所有路径沿用输出根、目录租约、拒绝 reparse 越界、不可覆盖文件发布和结构化错误机制。事件明文只写入本地时间线，不进入普通故障日志。

## 6. 容量与限制

300 秒是时间上限，不替代其他保护。建议初始值如下，均需实测后确认：

| 配置 | 建议 |
| --- | --- |
| segment_seconds | 默认 300；分段模式允许 1–300 |
| 单段媒体大小 | 约 192 MiB 提前轮转，256 MiB 硬预算 |
| 单段时间线 | 约 48 MiB 提前轮转，64 MiB 硬预算 |
| 单段观察数 | 接近现有采样/事件上限的 80% 时提前轮转 |
| 任务总磁盘预算 | 默认 2 GiB，可显式调整；包含临时数据、检查点日志与清单 |
| 任务墙钟上限 | 默认 8 小时，可显式调整；不是 8 小时续航承诺 |
| 磁盘剩余空间 | 建议保留至少 1 GiB，并满足当前段最坏收尾预留 |

提前轮转需要在下一帧/事件批次写入前检查可用预算，预留单次编码最坏上界和收尾空间；不能先突破硬预算，再删除整段。无法在预算内保存第一帧时，开始前拒绝或返回明确失败。

维持每段可被当前抽帧器读取：最大 300 秒 × 50 FPS 为 15,000 次常规采样，256 MiB 也低于现有 512 MiB 输入预算。检查点补帧等仍计入真实编码帧数，必须另外约束到读取器限制内；不能只凭乘法认定永远安全。

达到总预算的默认动作是停止保存。循环覆盖旧段不在本阶段范围。

## 7. 键鼠帧身份与跨段查询

- session ID 属于整次录制；observation ID 在段间递增。每段有独立 asset/frame ID。
- 每段时间线保留原始 UTC、采集区间和全局媒体位置；GIF 内时间从 0 开始。
- recording.json 为每段存储相对路径、segment ID、asset ID、全局半开时间区间、实际时长、轮转原因、提交状态和文件校验关联。
- 以 650 秒示例：全局 420 秒定位到 part-000002 的局部 120 秒；全局 300 秒属于下一段，不在两段重复计入时长。
- 边界画面复用可能使同一次真实采样对应多个输出帧；保留一对多映射。事件附近允许关联邻段采样，返回媒体所属段和被关联采样所属段，不能伪造事件时间或改写原始观察 ID。
- 暂停期间事件仍遵循既有记录策略；未对应画面时明确返回空映射。事件丢失、记录截断和降帧分别报告。
- timeline/frame_at/extract 接受 recording.json 或组目录，按索引定位单段后调用现有合成读取器。既有单 GIF 输入不变。
- 全局抽帧先按事件和段索引缩小范围，局部差分/二分只处理候选区间；不从第一段依次解码到数小时后的目标。
- 本阶段不做自动合并。未来的单 GIF 导出单独设计流式导出、容量限制和时间映射，不能直接拼接文件字节。

## 8. CLI 与 MCP 使用合约

以下为拟议接口，不是当前可执行命令。

CLI：

```powershell
# 前台宿主持有录制任务，直到 stop 或总预算到达；不安装服务
framelet record --mode segmented --name bilibili --output-dir D:\Captures --segment-seconds 300 --until-stop --session demo

# 另一个终端请求保存并停止
framelet stop --session demo

# 自动录制总计 650 秒，通常得到 300 + 300 + 50 秒
framelet record --mode segmented --name bilibili --output-dir D:\Captures --segment-seconds 300 --duration 650
```

分段模式的 output-dir 与普通模式的 output 是互斥入口，解析时显式检查，不能把已有 .gif 路径偷偷当目录。CLI 可经事件流输出每次 segment_committed，最终 stdout 返回组路径、状态和摘要。

MCP 扩展现有 framelet_start_recording 的显式 mode，并保留旧工具参数分支：

```json
{
  "mode": "segmented",
  "name": "bilibili",
  "segment_seconds": 300,
  "duration": 650,
  "request_id": "demo-recording-001",
  "region": {"x": 0, "y": 0, "width": 960, "height": 540},
  "fps": 10
}
```

MCP 输出位置仍受 context 的 output_root 限制。mode=segmented 时 duration 是有界任务时长，不沿用单 GIF 的 300 秒任务校验；每段仍不得超过 300 秒。until_stop 仍受墙钟和磁盘总预算约束。省略 mode 保持当前普通模式。

start 立即返回 session_id、组目录和 recording.json 路径。相同 request_id 与相同规范化参数返回已有任务，异参冲突；请求重试不能启动第二份录制。新 request_id 映射落盘，任务结束后也按明示保留期供查询。

status 返回 state、当前段号、已提交段数、recorded_ms、wall_ms、当前段时长、磁盘占用、最后检查点时间、告警和 next_poll_ms；不在每次查询返回无限增长的文件列表。新增分页 recording_list 发现活动/历史/待恢复任务；段清单分页获取。

分段模式 stop 立即请求保存，返回 finalizing，随后查询到终态。重复 stop 返回同一个任务结果。普通模式保留兼容合约。任务不要求 AI 持续调用 status 才运行；轮转和检查点由软件自身调度。

本阶段由现有 CLI/MCP 宿主监督 worker，不提供断连后继续录制，也不自动启动独立后台服务。MCP 被终止后 worker 随所属 job 结束；已保存组和恢复清单可由新进程发现并处理。跨客户端持续运行是后续单独能力。

## 9. 实施边界

1. 将普通录制参数和分段任务配置分开校验，避免用一段的 300 秒作为整个 worker 的退出期限。
2. 抽出连续采集/键鼠观察服务与可轮换 writer；设置总任务 deadline、检查点 deadline、轮转/收尾 watchdog，分别报告。
3. 实现组命名、段清单、检查点/有界日志、安全提交和幂等恢复。不得通过放开 Vec/文件上限达到长录制。
4. 接入 CLI/MCP start/status/stop/list，分组查询与抽帧复用已有服务；保持普通 GIF 路径兼容。
5. 完成实际 600 秒和跨两次轮转的录制与故障验收，再更新操作文档和简短 README 能力说明。

## 10. 验收标准

| 项目 | 验收 |
| --- | --- |
| 基本轮转 | 真实录制 650 秒，正常无提前触发时得到 300/300/50 秒，全部可独立打开 |
| 整数边界 | 实录总计 600 秒，仅两段；在 300 秒附近多次测试 stop，不产生空段或覆盖 |
| 身份命名 | 所有段前缀一致，编号递增，普通单 GIF 可清楚区分；重名并发开始不覆盖 |
| 边界连续性 | 使用带可见时间/帧号的真实渲染源，核查边界是否额外丢帧；异常则记录缺口 |
| 键鼠同步 | 轮转前后点击/按键各一次，ID 唯一不重置，UTC 保留，段归属/偏差正确 |
| 暂停 | 跨过真实 300 秒暂停，媒体时间不增加，不生成空段；墙钟保险仍有效 |
