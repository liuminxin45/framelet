# 长录制、清晰度与高帧率设计

状态：总体演进方案。基于 2026-11-02 本地开发版初始代码核对；第一阶段长录制已实施，实际入口以 [long-recording.md](long-recording.md) 为准。本文画质、高帧率、跨连接持久任务等新增参数仍为提案，不能作为当前命令执行。保留单个原生 EXE、无需额外安装运行时、CLI First 和 MCP 可发现的定位。

更新：用户已取消 200 FPS 目标，当前已实施最高 60 FPS，见 [60fps.md](60fps.md)。清晰度策略以 [fidelity-strategy-design.md](fidelity-strategy-design.md) 为准；本文 200 FPS 部分仅留作历史设计，不再实施。

第一阶段以 [最长单段 300 秒的可靠轮转录制](segmented-recording-design.md) 为准；其单段时长、命名、恢复与任务生命周期细节取代本文对应的概念建议。

## 1. 当前能力与约束

| 项目 | 当前实现 | 含义 |
| --- | --- | --- |
| MCP 阻塞录制 | `framelet_record`，最多 300 秒 | 产品校验，不是协议规定 |
| MCP 后台录制 | `framelet_start_recording` 立即返回，但同样最多 300 秒 | 克隆了阻塞工具 schema，dispatch 也重复校验 |
| CLI / GUI | 共享引擎校验最多 3600 秒 | GUI 启动时设置 3600 秒；暂停也计入墙钟上限 |
| 采样帧率 | CLI / MCP 1–50 FPS | GUI 下拉只有 10/16/20/25；实际采样率可能更低 |
| 输出像素预算 | 输出宽 × 高 × 请求 FPS ≤ 80,000,000 | 是当前工程保护值，不是硬件实测极限；不覆盖缩小前的全部采集成本 |
| 空间精细度 | `max_width` 等比例缩小，不放大，面积平均重采样 | 改变输出像素尺寸；默认原尺寸 |
| 颜色处理 | `quality=1..30`，1 偏向更充分量化，30 偏向速度 | 不是百分比清晰度，也不是 JPEG 质量或目标码率；无独立颜色数/抖动策略入口 |
| 压缩 | 完全相同画面合并停留时长、变化区域编码 | 不等同于主动降采样；GIF 调色板转换本身可能损失颜色 |
| 文件和时间线 | GIF 默认 256 MiB，可设至 1024 MiB；采样 200,000 条、输入事件 100,000 条、时间线 64 MiB | 事件/采样容量到顶会影响记录完整性 |
| 后续读取 | 帧遍历最多 100,000 帧，输入最多 512 MiB | 当前写入预算可大于读取预算，长录制必须解决该不一致 |
| 生命周期 | MCP 断连取消未完成录制；子进程受父进程 job 管理 | 有故障隔离，但尚不是跨客户端重启的持久任务 |

代码依据：`src/mcp/catalog.rs`、`src/mcp/dispatch.rs`、`src/sessions.rs`、`src/recording/{options,mod}.rs`、`src/encode.rs`、`src/frames.rs`、`src/timeline/{model,store}.rs`、`src/worker.rs`、`src/gui.rs`。

## 2. 推荐方案：持久任务 + 分段录制 + 按需导出单 GIF

### 为什么不只提高 300 秒

阻塞请求确实可能触发宿主的工具调用超时，但 MCP 并不要求整个录像过程停留在一个请求里。现有后台接口已经证明可以立即返回。增加一个数值不会解决文件过大、元数据增长、断电损失、停止等待、抽帧遍历耗时等问题。

统一采用：短请求创建任务 → 返回任务 ID → 实际录制独立运行 → 查询/控制/导出使用短请求。先保留现有 start/status/stop 工具以兼容普通客户端；支持 Tasks 的客户端经协商后复用相同任务内核，不维护两套录制逻辑，也不把某一版 Tasks 扩展作为安装前提。

### 使用体验与 API 合约

- 保留已有 5 秒默认和短录制行为。只有显式长时长或 `until_stop:true` 才创建长录制工程，避免升级后意外持续录制。
- `start_recording` 接受稳定 `request_id` 作为幂等键。同一个键和参数返回原任务；同键异参报冲突。创建超时后允许安全查询/重试，不自动重复录屏。
- 新增 `recording_list`，客户端重启后发现可接管的本用户任务。`status` 返回 `next_poll_ms`，建议初始 1 秒、稳定时 3–5 秒；录制不依赖 AI 持续轮询。
- `stop` 和 `cancel` 立即返回当前状态，不在工具请求里等待长时间收尾。`stop` 保存，`cancel` 仅删除当前未提交分段，已提交内容保留；完整删除工程是独立显式操作。该变化需要明确的新版本合约。
- `export` 返回独立导出任务，可选择整个工程、某一时间区间或分段列表。保持旧的短录制返回单 GIF；长录制返回工程清单及可直接查看的分段。
- 同一套任务提供 CLI 的 start/status/list/stop/export 命令。CLI 默认输出结构化 JSON，GUI 显示时长、已保存内容、容量和停止按钮。

### 所有者与断连

同一个 EXE 按需启动本用户录制管理进程，通过有本用户 ACL 的 Windows 命名管道通信；无安装服务、无网络监听、无开机常驻。管理进程持有 worker 的 kill-on-close job，而非短命的 MCP 适配进程。没有活动任务/导出后自动退出。

默认绑定连接：适配进程自动发送存活信号，不要求模型调用续租工具。连接断开后给予建议 30 秒重连窗口，超时自动停止并保存，避免无人管理的持续键鼠采集。显式 `lifecycle:detached` 才允许断连后录到停止或预算上限；必须有有界墙钟期限。本地 GUI/托盘提供可见状态及停止入口；这个行为是对当前 EOF 取消策略的有意升级。

开始前检查磁盘、权限、输出根、互斥、桌面可用性。状态机为 preparing → recording / paused → finalizing → completed / partial / failed；告知停止原因，如 user_stop、wall_limit、disk_budget、source_lost、worker_timeout。`partial` 必须列出有效内容和缺口，不能伪装完整成功。控制请求幂等，终态不可逆。

### 分段与数据持久化

建议初始配置如下，均为待压力测试的工程起点，不是已验证的最佳值：

| 配置 | 建议 |
| --- | --- |
| 正常分段 | 最长 60 秒，或接近 64 MiB 时提前收尾 |
| 额外分段触发 | 时间线条数/字节预算、尺寸或采集配置变更 |
| 长录制墙钟保险上限 | 默认 8 小时，可显式配置；不开放无界录制 |
| 总磁盘预算 | 默认 2 GiB，用户可调；包含时间线、临时文件和导出占用 |
| 磁盘保留 | 建议至少 1 GiB 可用空间，同时预留当前分段收尾和清单空间 |
| 默认到达预算行为 | 停止并保留已提交段；不自动覆盖旧段 |

上述预算会提前终止某些录制，8 小时不是续航承诺。分段大小是软目标，必须另外设每段硬上限和下一帧最坏写入预留；预估不足不能直接丢弃整个工程。

工程包含 `recording.json`、`segments/000001.gif`、每段时间线和校验清单。每段第一帧是完整画面且可独立解码；段清单保存全局起止时间、尺寸、哈希和已提交状态。先写并刷新分段，再发布提交清单；尾部不完整段不进入已提交列表。崩溃恢复只接受已提交或验证后可恢复内容，绝不合成未采到的事件。

元数据按段/有界日志持续写盘并建时间索引，不把数小时事件留在一个 Vec 或 JSON 内。每个采样/键鼠事件仍使用全局 session ID + observation ID，跨段不重置；段和导出有独立 asset ID。跨段边界附近的事件可以关联相邻段的采样，保留真实偏差和没有画面的事件。键鼠输入时间线与图像降帧解耦。

分段不应通过周期性停止并重启整个 worker 实现：采集/输入观察应连续，编码器轮换。编码/写盘变慢用有界队列与明确丢帧记录；不能声称切段天然零缺口。遇到持续堵塞，结束为 partial 并记录时间区间。

### 恢复、抽帧与导出

- 清单使用全局单调时间区间索引；先定位段，再在该段内合成解码。GIF 有帧依赖，不能仅凭字节偏移任意跳帧。
- Agent 先按键鼠事件缩小区间，再粗采样/数值差分、局部二分、最后少量视觉复核。仅适用于局部“静止→动作”边界的二分；全片多次运动不能假设单调。
- 导出单 GIF 时流式读取分段并处理调色板、disposal、完整首帧和全局时序。不能简单拼接 GIF 字节。先实现正确的合成再编码路径，后续考虑经验证的编码块复用以减少重复量化。
- 导出不加载整片，单独限制内存、时间、像素和输出大小；超限保留工程并建议导出区间。修改读取器/编辑器/时间线查询共同支持工程，不能仅放宽录制限制。超大单文件读取走显式长文件模式，而非移除所有输入防护。
- 多文件提交仍不宣称跨文件原子或抵御磁盘损坏；最后提交的索引决定有效段集合。

## 3. 清晰度：分开控制像素、颜色和时间

同样的显示尺寸和同样的像素尺寸是两件事：把 960×540 图放大显示为 1920×1080 不会恢复文字细节。保持 GIF 本身 1920×1080 时，所谓降低“分辨率”只能是内部降采样后放大，实质是模糊/像素化，不应该作为默认压缩办法。DPI 元数据不能替代有效像素。

建议新增三个高级入口，并以少数预设覆盖日常使用：

| 维度 | 建议参数/策略 | 约束 |
| --- | --- | --- |
| 空间 | `scale` / `max_width` / 固定输出尺寸；area 或 Lanczos 重采样 | 明确互斥与宽高比；文字优先原尺寸；尺寸切换只能新段 |
| 颜色 | `colors=32/64/128/256`、`dither=off/ordered`、稳定的段级调色板，必要时局部调色板 | 小文字优先 256 色和弱/无抖动；渐变可有序抖动；调色板漂移会闪烁 |
| 时间 | `capture_fps`、`gif_fps`；可选静止检测及事件附近加密采样 | 保留真实时长，不隐式加速；按键/点击优先保留邻近帧 |

保留旧 `quality` 兼容，并在文档中重命名解释为量化计算投入；新增参数不要把它包装成“画质百分比”。GIF 单个调色板最多 256 项，不能承诺任意全彩屏幕无损。逐帧/局部调色板不同，整段可出现超过 256 种颜色，但无法取消单个色表的限制。

段级调色板从有界短窗口训练并冻结，不能为等待整段结束而缓存全部原始帧；遇到新场景按规则切段或使用局部调色板。抖动采用确定性坐标基准，避免变化区域裁剪导致图案跳动。持续控制色彩质量与编码成本，不能只减小色数后假定一定更快或更小。

| 预设 | 建议起点 | 主要用途 |
| --- | --- | --- |
| `test` | 原尺寸，1–5 FPS，256 色，关闭抖动，输入事件持续记录 | 状态验证、截图比较；快速瞬态需提高帧率 |
| `demo` | 原尺寸或显式 max_width，目标 30 FPS，256 色，稳定颜色 | 软件演示、滚动展示；预算不足时如实告知实际能力 |
| `compact` | 建议最长边 960，10–15 FPS，128 色，弱有序抖动 | README 分享、小文件；告知会损失细节 |
| `precision` | 原尺寸，最高 200 FPS 采集到独立源工程；另导出 ≤50 FPS GIF | 瞬态检查、慢动作；依赖硬件预检 |

自适应模式首先减少重复采样/重复编码和量化计算投入，再在允许范围内降帧；不静默改变文字尺寸、区域或掩码。严格模式达不到要求就返回 capability_insufficient 或 partial，不能偷偷降级后宣称达标。近似静止检测可能漏掉小字/光标，证据模式默认只合并完全一致像素。

录制前建议用显式、短时、同区域/掩码校准，返回预计耗时和预算，销毁校准帧；明确它不是正式记录，也不能预测后续复杂场景。正式状态返回 requested/effective FPS、色彩策略、丢帧、实际输出尺寸和降级原因。

## 4. 200 FPS：支持采集，独立设计源数据与 GIF 输出

GIF89a 的正帧延时单位是 1/100 秒。200 FPS 需要 5 毫秒，不能用单帧正延时准确表示；0 延时没有可移植的 5 毫秒语义。10 毫秒意味着 100 FPS，但播放器仍可能钳制短延时。兼容 GIF 输出继续建议 1–50 FPS，30 FPS 用 30/30/40 毫秒等累计误差控制分配，保持总时间。

因此不能把当前 `fps <= 50` 改成 200 就宣传支持 200 FPS GIF。当前循环对每次写入最少给 1 个厘秒，直接提高上限会产生播放时长偏差；必须先拆开采集调度、原始时间和输出重采样。

### 高速架构

1. 保留现有 GDI 为兼容后端。新增 DXGI Desktop Duplication，后续评估 Windows Graphics Capture；按区域/窗口需求和能力选择后端，失败时报告切换及采集间隙。
2. 采集线程只采集、时间戳和投递；变换/掩码、编码、写盘分阶段。隐私处理必须在画面进入任何持久存储/预览之前完成。
3. 使用预分配的 2–4 槽有界缓冲，GPU/CPU 两侧都设字节上限；不随录制时长增长。利用 dirty/move 信息减少工作，避免每帧全屏 GPU→CPU 拷贝。
4. 请求 `capture_fps=200`，记录来源 present 时间、采集开始/完成时间、实际有效更新率、重复采样和丢失更新。60 Hz 常规桌面不会因轮询 200 次变成 200 个不同画面；需高刷新显示/源更新以及足够采集能力。多显示器分别报告时序，不能假设硬件同步。
5. 将原始或可恢复的帧源保存到有界分段工程，支持区域无损关键帧/差分帧和索引，提供逐帧 PNG 导出。若丢弃高频原始像素只保留 30 FPS GIF，不能声称支持 200 FPS 的事后逐帧检查。
6. 无损帧源的磁盘开销可能很大；先实现短时高速突发/环形缓存，触发后导出事件前后窗口。环形覆盖只允许用户明确选择，并报告被覆盖区间。长时高速录制必须先验证磁盘吞吐和总预算。
7. GIF 输出对源数据按真实时间重采样至 30/50 FPS，优先保留事件附近画面。精查 200 FPS 时可导出 4 倍慢动作的 50 FPS GIF，同时保存原始时间映射；慢动作不等同于实时 200 FPS 播放。
8. 如需长时实时高帧率视频，可评估 Windows Media Foundation 的系统编码器作为可选导出；需探测编码器/分辨率/帧率，不承诺所有系统存在或支持 200 FPS，不把 FFmpeg/额外运行时变成安装前提。

### 性能边界

当前 80 MP/s 输出预算意味着原尺寸 1920×1080 最多允许请求 38 FPS，3840×2160 最多 9 FPS；“参数最高 50”并不表示任意尺寸都能 50 FPS。

200 FPS 下，1920×1080 是 414.72 MP/s；仅一次 4 字节/像素的完整搬运约 1.66 GB/s，尚未包含多次复制、量化和编码。若沿用 80 MP/s 预算，200 FPS 仅能容纳 400,000 输出像素，如 800×500。这些是算术预算，不是当前支持 200 FPS 或硬件实测结果。

能力预检分别评估采集、变换、编码与磁盘，拒绝用整体一个 MP/s 数字替代所有瓶颈。状态至少提供 `requested_fps`、`capture_fps_actual`、`source_updates_fps`、`encoded_fps`、`dropped_samples`、`source_accumulated_frames`、队列峰值、写盘吞吐和端到端耗时；相同像素合并不是采集丢帧。

键鼠观察保留独立队列与统一 observation ID；记录真实采集区间和偏差，不根据 200 FPS 自动宣称 ±2.5 毫秒精度。系统调度、事件 hook 和采集时延仍须实测。

## 5. 实施顺序与验收

### 第一阶段：长录制与可靠保存

统一后台任务/幂等控制、分段持久化、事件索引、预算停止、断连接管，先跑通当前帧率下的完整工作流。验收：跨越 300 秒和 3600 秒的实际录制、明确环境下 8 小时压力录制；内存随时间有界；随机杀进程/断连/磁盘满/目录权限变化/睡眠唤醒后，已提交段仍可独立打开并抽帧；失败阶段、丢失时间和恢复路径准确。比较切段前后时序与原始 observation ID，无重复点击/重复录制。

### 第二阶段：清晰度预设

实现像素/颜色/时间三个独立配置与预检。用小字体、代码编辑器、暗色界面、渐变、快速滚动和掩码场景对照：文字可读性、颜色闪烁、帧时长、体积和 CPU。证据模式不得用近似静止检测默默删除变化。先明确支持 SDR；HDR 采集需显式色彩转换策略，不能直接当 SDR 字节解释。

### 第三阶段：高速采集与源工程

先在小区域、高刷新源、短时突发验证 60/100/120/200 FPS，再扩大分辨率/时长。使用带可见帧序号的真实渲染源测有效更新、遗漏、重复和键鼠偏差；报告显示刷新率、CPU/GPU、采集区域和后端。测试源不足 200 Hz 时的明确提示、性能不足的严格失败/自适应降级、队列堵塞与进程终止。GIF 独立验证浏览器和 Minimal Image Viewer 的总时长与慢动作映射，不能仅看配置字段即宣布 200 FPS 达成。

工程与 API 文档放在 docs，README 只在功能实现并验收后增加简短能力说明。`framelet_context` 发布实际能力及限制；不要提前把本方案的参数当成已发布功能。

- [Microsoft Desktop Duplication API](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/desktop-dup-api)：GPU 表面、dirty/move 信息及鼠标处理。
- [DXGI_OUTDUPL_FRAME_INFO](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_2/ns-dxgi1_2-dxgi_outdupl_frame_info)：来源 present/鼠标时间戳、累计更新与受保护内容标识。
